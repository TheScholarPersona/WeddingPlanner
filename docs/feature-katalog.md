# Feature catalog

A checked overview of what the Wedding Planner can do. For the product side it describes each
feature in plain words; for development it lists the endpoints, pages, jobs and tests behind it.
Only features proven by passing tests are in the catalog. Everything else sits in the review list.

- **Source of truth:** YAML in [`catalog/`](../catalog). The view, the JSON and the figures are
  generated from it.
- **View:** CI artifact `feature-catalog` (`index.html`), or run `make catalog-full` locally and
  open `catalog/dist/index.html`.
- **Tool:** [`tools/feature_catalog/`](../tools/feature_catalog), a separate Python package.
  The application does not depend on it.

## Layout

```
catalog/
  catalog.yaml            areas, groups, what each area owns, test runs, exclusions
  features/<area>.yaml    features with acceptance criteria and evidence
  review.yaml             features that are not (fully) proven yet, with state and reason
  discovered/             generated by tests, committed: backend.json, frontend-routes.json
```

`catalog/discovered/` comes from two tests. The application code stays unchanged:

- `backend/tests/test_catalog_export.py` exports all API routes. For each route it records the
  roles that may call it (derived from its permission), its handler, the worker jobs and the
  CLI commands.
- `frontend/src/app/routes.catalog.test.tsx` exports all pages of the router with component and
  guard.

Both tests fail when the file is out of date. `make catalog-export` refreshes them.

## Rules

1. **One feature is one usable capability.** It is not one endpoint and not one module. Two
   levels: plain description (`summary`, `description`, `usage`, `rules`) and `technical`.
2. **Acceptance criteria bridge description and tests.** Every feature needs at least one
   criterion of kind `effect`. Every rule that names an error code in backticks (`` `too_many_images` ``,
   `` `403` ``) needs a criterion of kind `rule` with that `code`.
3. **Evidence names what it proves.** Each evidence lists the criteria it `covers`. A feature is
   *proven* only when every criterion has evidence that passed in the last run.
4. **A test proves something only when it acts and asserts.** It triggers the feature through an
   endpoint, page, job or component, and it asserts an observable effect (a value, stored state,
   an email, what the page shows) or the refused action with its code. A status code alone is
   enough only for a rule. Mock-based unit tests count for UI logic and pure calculations.
5. **Never evidence:** smoke tests, skipped tests, tests that did not run, tests that only check
   what they mocked. The Playwright tests run against the full Docker stack in CI and count as
   evidence for the end-to-end flows (criteria `e2e-…`).
6. **Review duty.** Whoever adds or changes evidence reads the test. Changes under
   `catalog/features/` need a review (CODEOWNERS).
7. **The tool never adds features.** It reports unassigned parts, dead references and missing
   evidence. People decide.

## Checks

`python -m feature_catalog check [--reports DIR]` reports:

| Code | Level | Meaning |
|---|---|---|
| `SCHEMA` | error | invalid YAML, unknown key, wrong group or id, part claimed twice |
| `UNOWNED` | error | discovered part that no area claims |
| `UNASSIGNED` | error in catalogued areas, note in open ones | part without a feature or exclusion |
| `UNKNOWN_ENDPOINT` / `_JOB` / `_COMMAND` / `_ROUTE` | error | reference to something that no longer exists |
| `UNKNOWN_COMPONENT` / `UNKNOWN_TEST` / `UNKNOWN_DEPENDENCY` | error | missing file, test or feature |
| `EVIDENCE_MISSING` / `ACCEPTANCE_MISSING` | error | no evidence / no criterion of kind effect |
| `RULE_WITHOUT_ACCEPTANCE` | error | rule code without a criterion |
| `EVIDENCE_UNLINKED` / `EVIDENCE_KIND` | error | evidence without `covers` / wrong test kind |
| `ACCEPTANCE_UNCOVERED` | error | criterion without passed evidence |
| `EVIDENCE_NO_ASSERTION` | error | test body without any assertion |
| `RULE_CODE_NOT_ASSERTED` | error | the rule's code does not appear in its tests |
| `EVIDENCE_FAILED` / `EVIDENCE_SKIPPED` / `EVIDENCE_NOT_RUN` | error | test failed, skipped or not in the report |
| `REPORT_MISSING` | error | no JUnit report of a configured test run |
| `EVIDENCE_STATUS_ONLY` | warning | test covering an effect only checks status codes |
| `EVIDENCE_UNRELATED` | warning | test touches no part of the feature |
| `ENDPOINT_UNTESTED` | warning in catalogued areas | no test calls the endpoint recognizably |

Areas claim parts by prefix. `/orgs/{org_id}/clients` owns itself and everything below it, but
not `/orgs/{org_id}/clients-export`. An entry with a method owns exactly that endpoint. The most
specific area wins.

Test reports are recognized by their content, not by the file name:

| Report | Recognized by |
|---|---|
| pytest backend | suite `backend` |
| catalog tool | suite `feature-catalog` |
| vitest | suite `frontend-unit` |
| Playwright | `*.spec.ts` test classes |

Without `--reports` the check is static only.

## Commands

| Command | What it does |
|---|---|
| `make catalog` | static check (YAML, code, test code) |
| `make catalog-export` | refresh `catalog/discovered/` after changing routes, jobs, commands or pages |
| `make catalog-full` | run all tests with JUnit reports, then check and build the view |

CI runs the `catalog` job after backend, frontend and e2e. It downloads their reports, runs the
tool's own tests, checks the catalog against all reports and uploads the view as artifact
`feature-catalog`.

## Upkeep

- **New capability:** add a feature with criteria and evidence, or an entry in `review.yaml` with
  a reason.
- **New endpoint, page or job:** run `make catalog-export`, then assign it to a feature or add an
  exclusion with a reason.
- **Renamed test:** update the evidence (`UNKNOWN_TEST`).
- **Removed capability:** delete the feature. Never reuse its id.
- **Area done:** set `status: catalogued`. From then on unassigned parts are errors.
- **YAML:** quote values that contain `: ` or start with a backtick or `*`. Inside `{ … }`, also
  quote values with commas.

## Gaps found while cataloguing

Cataloguing showed behaviour that no test checked. 50 tests were added along the way, and 19
existing assertions now also check the error code, not only the status:

| Area | What had no test |
|---|---|
| Moodboards | sections, limits, team hearts, the couple's image access, arranging and deleting own boards, team-only comments |
| Account & sign-in | profile, cancelling the code step, new recovery codes, a wrong password confirmation, platform admins keeping two-factor on, the no-access page |
| Data protection | cleanup of old reset links, invitations and the notification log; the erase dialog |
| Couple's portal | withdrawing an open invitation, who manages the couple's access, the More page |
| Platform operations | the CLI commands, resetting another platform admin, the support view page, granting support in the settings |
| Organization & team | withdrawing a team invitation, the settings page |
| Weddings | restoring from the archive, milestones, changing or removing team members, the wedding list page |
| Tasks & templates | sorting and deleting tasks, editing checklist items, the couple's checklist and reopening, editing or deleting templates |
| Budget | categories, removing items and payments |
| Clients and Vendors | editing clients and contacts, deleting a client without weddings, editing vendors, removing a vendor from a wedding, all three pages |
| Calendar | the couple checking and revoking their subscription |
| Comments & notifications | the couple's notification settings, sending by SMTP, the `send-digests` command |
| Documents | nothing; the area was fully covered |

Two findings were not about tests:

- The route protection test had stopped checking anything after a FastAPI update. It now fails if
  it sees fewer than 150 routes.
- Restoring an archived wedding always set its status to completed, even for a wedding still ahead.
  It now follows the wedding date: planning if the day is still ahead, completed once it has passed.

## Next steps

- Keep the catalog current (see Upkeep): every new endpoint, page or job needs a feature or an
  exclusion, otherwise CI fails.
- New end-to-end flows in `frontend/e2e/` can be added as evidence (kind `e2e`) to the features
  they walk through.
